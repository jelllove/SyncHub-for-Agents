# AI Readiness Evidence Pack Design

## Goal

Improve the repository's truthful AI-readiness evidence without changing SyncHub
application behavior, fabricating agent activity, or adding governance rules that
block a single maintainer from merging validated work.

## Context

The latest default codeblend assessment for the current feature branch reported
63.8 overall, with Substrate 78.2 and Operation 52.0. The weak axis is Operation:
self-healing, observability, human-loop, agent surfaces, and agentic throughput
remain under-evidenced. The same report also lists deterministic Substrate gaps:
no environment example, no versioned specs, and insufficient modularity evidence.

The project already has a green, non-blocking native validation baseline:
Windows source-bound receipts, Linux race and frontend checks, security checks,
three-platform packaging smoke tests, and contained diagnostic repair/rollback
proof. The next optimization must make that evidence easier for humans and
automation to find while preserving the existing safety boundaries.

## Approach options

### Option A: Non-blocking evidence pack

Add a safe environment template, versioned report schemas, repository label
configuration, an agent observability guide, and executable checks that keep the
evidence files aligned with the workflows and validation report shape.

Benefits:

- Directly addresses recognized Substrate gaps: `env_example` and
  `versioned_specs`.
- Adds concrete, reviewable observability and governance metadata without
  requiring another reviewer.
- Does not mutate app behavior or user sync data.
- Can be validated locally and in hosted CI.

Trade-off: this may improve score, but it cannot honestly prove production
self-healing or confirmed agent-authored PR throughput by itself.

### Option B: Strict governance

Require approving reviews and CODEOWNERS enforcement in the default branch ruleset.

Benefits:

- Likely restores or improves policy, human-loop, and throughput floors when the
  evaluator reads default-branch API evidence.

Trade-off: this repository appears to have one collaborator. Requiring approval
from another actor could block routine merges or force admin bypasses, which
would weaken the actual operating model.

### Option C: Full agent operation enablement

Create live GitHub Copilot coding-agent tasks and merge agent-authored PRs after
review.

Benefits:

- This is the most legitimate path toward Operation 80+.

Trade-off: the account previously received 403 Forbidden when attempting cloud
coding-agent work. Without that capability and real agent-authored merged PRs,
the repository cannot honestly demonstrate this dimension.

## Selected design

Use Option A now. It is the highest-confidence improvement that preserves app
behavior and mergeability. Do not claim that this alone guarantees an 80+ score.
After implementation, run the bundled evaluator once and report the actual
score. If the score remains below 80, document the remaining external blockers:
unavailable approved local-loop verification profile, unrecognized diagnostic
repair evidence, and unavailable Copilot coding-agent provenance.

## Files and responsibilities

- `.env.example`: documents non-secret optional development inputs and keeps
  secret patterns ignored.
- `.github/labels.yml`: declares the labels used to route agent, validation,
  repair, dependency, and documentation work.
- `CODEOWNERS` and `.github/ISSUE_TEMPLATE/config.yml`: document non-blocking
  human review ownership and stale-validation routing without requiring a second
  approver.
- `.github/workflows/self-healing.yml`: performs read-only CI failure response by
  publishing bounded repair proposals after failed CI signals; it never commits,
  opens issues, opens PRs, or claims production self-healing.
- `docs/specs/validation-receipt.v1.schema.json`: versioned contract for
  validation receipts generated by `node scripts/dev.mjs verify`.
- `docs/specs/repair-proof.v1.schema.json`: versioned contract for contained
  repair proof receipts generated by `node scripts/dev.mjs repair:verify`.
- `docs/operations/agentic-observability.md`: maps workflows, reports, labels,
  and review handoffs to observable agentic work.
- `docs/reports/agentic-validation-reports.md` and
  `docs/dashboards/agentic-readiness-dashboard.json`: provide report and
  dashboard entry points for automation.
- `docs/runbooks/ci-failure-response.md`: describes detection, containment,
  remediation proposal, validation, and rollback handoff.
- `.vscode/mcp.json` and `tools/mcp/validation-server.mjs`: expose a local
  read-only MCP surface for validation-command discovery and documentation drift
  checks.
- `scripts/doc-drift.mjs`: deterministic checker that verifies the evidence
  docs mention the required workflows, artifacts, labels, and schema versions.
- `scripts/dev.mjs` and `scripts/dev-lib.mjs`: expose the checker through the
  existing `docs` and `check` commands.
- `frontend/doc-drift.test.mjs`: synthetic tests for the checker.
- `tools/repocheck/workflow_test.go`: guard that the labels and schema docs stay
  committed and that the workflows still publish the documented artifacts.
- `docs/development.md`: documents the new evidence contracts and drift check.

## Data flow

Validation and repair commands continue to produce runtime JSON/JUnit/HTML
artifacts under ignored `.artifacts/`. The new versioned schemas describe those
artifacts and the documentation guide explains where hosted workflow artifacts
are published. The drift checker reads repository files only, confirms that the
documented workflows and artifact names still exist, and fails closed when a
referenced schema, label, or workflow artifact contract is missing.

## Error handling and safety

The new checker must throw explicit errors for missing or contradictory evidence
references. It must not create, delete, modify, upload, or publish any runtime
artifact. It must not read ignored dependency directories, real user sync
repositories, credentials, or local skill binaries. Existing source-bound
verification behavior remains authoritative for command execution.

## Testing and verification

1. Add failing tests for the new drift checker before implementation.
2. Add workflow/configuration guards for labels and schemas.
3. Run the targeted tests until they pass:
   - `npm --prefix frontend run test:lint`
   - `go test ./tools/repocheck -count=1`
4. Run repository-standard validation:
   - `node scripts/dev.mjs check`
5. Push the branch and verify the hosted PR checks.
6. Run one full codeblend evaluation and report the actual result.

## Out of scope

- No release or tag creation.
- No app behavior changes.
- No automatic source-modifying repair.
- No GitHub issue creation solely for scoring.
- No fake MCP server, fake incident history, fake agent-authored PR, or evaluator
  rule modification.
- No new required-review rule unless the maintainer explicitly approves the
  resulting merge constraint.
